# 🎵 音频编码术语详解

本文档解释小智语音助手项目中使用的音频编码参数，帮助理解语音通信的技术原理。

## 项目中的音频参数

```
采样率:    16000 Hz
声道数:    1 (单声道)
帧大小:    960 samples (60ms)
比特率:    16 kbps
复杂度:    5
```

---

## 1. 采样率 (Sample Rate) - 16000 Hz

### 什么是采样？

声音是连续的波形，但计算机只能处理离散的数字。**采样**就是每隔一小段时间，记录一下声音波形的高度值。

```
真实声波:     ∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿
              ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓  (采样点)
数字化后:     • • • • • • • •
```

### 采样率 = 每秒采样多少次

| 采样率 | 应用场景 | 音质 |
|--------|----------|------|
| 8000 Hz | 电话通话 | 较低，但够用 |
| **16000 Hz** | 语音识别/语音助手 | 语音清晰，适合人声 |
| 44100 Hz | CD 音乐 | 高保真 |
| 48000 Hz | 专业音频/视频 | 专业级 |

### 为什么选 16kHz？

根据**奈奎斯特定律**（Nyquist Theorem）：
- 要完整还原某个频率的声音，采样率必须是该频率的 **2 倍以上**
- 人说话的频率主要在 **300-3400Hz**
- 16kHz 采样率可以捕捉到 8kHz 以内的频率，完全覆盖语音范围
- 同时 **数据量小**，适合网络传输和嵌入式设备

---

## 2. 声道数 (Channels) - 1 (单声道)

### 声道 = 有几路独立的声音

```
单声道 (Mono):    🔊 ← 一路声音，所有喇叭播同样的内容

立体声 (Stereo):  🔊←→🔊 ← 左右两路，有空间感

5.1 环绕声:       🔊🔊🔊🔊🔊🔊 ← 六路声音，电影院效果
```

### 常见声道配置

| 类型 | 声道数 | 应用场景 |
|------|--------|----------|
| **单声道 (Mono)** | 1 | 语音通话、语音助手、广播 |
| 立体声 (Stereo) | 2 | 音乐播放、游戏 |
| 5.1 环绕 | 6 | 电影院、家庭影院 |
| 7.1 环绕 | 8 | 高端影院 |

### 为什么用单声道？

- 语音助手只需要传输人声，不需要空间感
- 单声道 **数据量最小**（是立体声的一半）
- **延迟最低**，适合实时通信

---

## 3. 帧大小 (Frame Size) - 960 samples (60ms)

### 帧 = 一次处理的音频数据块

音频不是逐个采样点处理的，而是**一批一批**处理。每一批叫做一个"帧"。

```
采样点: ●●●●●●●●●●|●●●●●●●●●●|●●●●●●●●●●|...
        ←─────────→←─────────→←─────────→
           第1帧       第2帧       第3帧
         (960 点)   (960 点)   (960 点)
```

### 帧大小与时间的关系

```
时间(秒) = 采样点数 ÷ 采样率

60ms = 960 ÷ 16000 = 0.06 秒
```

### Opus 支持的帧大小

| 帧大小 (ms) | 采样点数 (16kHz) | 特点 |
|-------------|------------------|------|
| 2.5 ms | 40 | 极低延迟，效率低 |
| 5 ms | 80 | 低延迟 |
| 10 ms | 160 | 常用于实时通信 |
| 20 ms | 320 | 平衡选择 |
| 40 ms | 640 | 较高效率 |
| **60 ms** | **960** | **本项目使用** |

### 为什么选 60ms？

- **压缩效率更高**：每帧的开销被更多数据分摊
- **延迟可接受**：60ms 对语音交互来说感知不明显
- **Opus 推荐值**：特别适合语音应用

---

## 4. 比特率 (Bitrate) - 16 kbps

### 比特率 = 每秒传输多少数据

- **bps** = bits per second (比特每秒)
- **kbps** = kilobits per second (千比特每秒)
- 16 kbps = 16,000 bits/秒 = 2,000 bytes/秒 = **约 2 KB/秒**

### 原始数据 vs 压缩后数据

**原始 PCM 数据量计算：**
```
每秒数据 = 采样率 × 声道数 × 每采样位数
        = 16000 × 1 × 16 bits
        = 256,000 bits/秒
        = 256 kbps
```

**Opus 压缩后：16 kbps**

**压缩比：256 ÷ 16 = 16 倍！**

### 不同格式的比特率对比

| 格式 | 比特率 | 每分钟大小 | 用途 |
|------|--------|-----------|------|
| 原始 PCM | 256 kbps | ~1.9 MB | 未压缩音频 |
| **Opus (语音)** | **16 kbps** | **~120 KB** | 语音助手 |
| Opus (音乐) | 64-128 kbps | 480KB-1MB | 语音通话+音乐 |
| MP3 | 128-320 kbps | 1-2.4 MB | 音乐文件 |
| AAC | 128-256 kbps | 1-1.9 MB | 流媒体 |
| FLAC (无损) | 800-1400 kbps | 6-10 MB | 高保真音乐 |

### 16 kbps 够用吗？

对于语音（非音乐）场景：
- Opus 16 kbps 的音质 ≈ 传统编码器 32-48 kbps
- 人声清晰可辨，完全够用
- **节省带宽**，适合物联网和移动网络

---

## 5. 复杂度 (Complexity) - 5

### 复杂度 = 编码器的"努力程度"

Opus 编码器有一个 0-10 的复杂度设置，控制编码时使用多少 CPU 资源来优化音质。

```
复杂度:  0 ────── 5 ────── 10
         │       │        │
CPU占用: 低      中       高
编码速度: 快      中       慢
音质:    一般    好       更好
```

### 复杂度分级

| 复杂度 | CPU 占用 | 适用场景 |
|--------|----------|----------|
| 0-3 | 低 | 资源极其受限的设备、大量并发编码 |
| **4-6** | **中** | **嵌入式设备、Web 端、一般应用** |
| 7-10 | 高 | 高质量录音、对音质要求极高的场景 |

### 为什么选复杂度 5？

- **平衡选择**：音质与 CPU 占用的最佳平衡点
- **适合设备**：ESP32 和网页端都能较好处理
- **语音足够**：语音场景对音质要求不如音乐严格

## 📊 数据流动完整示意

```
【录音端 - 客户端】

  麦克风采集
      ↓
  原始音频 (16kHz, 单声道, 16-bit)
  数据率: 256 kbps
      ↓
  每 60ms 收集 960 个采样点
      ↓
  Opus 编码 (复杂度 5)
      ↓
  压缩数据 (约 120 字节/帧)
  数据率: 16 kbps (压缩 16 倍)
      ↓
  WebSocket 发送 (二进制)


【播放端 - 客户端】

  WebSocket 接收 (二进制)
      ↓
  缓冲队列 (等待 6 帧后开始播放)
      ↓
  Opus 解码
      ↓
  还原 PCM (960 采样点/帧)
      ↓
  AudioContext 播放
```
